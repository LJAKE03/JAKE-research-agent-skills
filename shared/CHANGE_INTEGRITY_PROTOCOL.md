# 原生一致性与科研可追溯变更协议

本协议用于修改 Skill、代码、脚本、Schema、配置、模板、说明文档或测试。它不是新的 Skill、Agent 或审批层；它只规定一次变更怎样在活动文件中形成一致的最终状态，同时保留科研和工程审计链。

## 1. 双重目标

- **原生一致性**：当前有效的活动文件应呈现为一套连贯设计，不依赖层层补丁、重复规则、隐含同步或无退出条件的临时分支。
- **科研可追溯**：原始数据、来源定位、关键参数、异常、失败记录、否定结果、决策依据、复盘、版本历史和变更说明必须可恢复与复核。

整洁活动状态不等于抹除历史。任何优化若让结论更难复核、让数据条件丢失或让失败路径不可恢复，均不算有效优化。

## 2. 根因与唯一权威来源

1. 先定位根因、权威文件、全部活动消费者和生成链，再修改实现。
2. 一个易漂移契约只保留一个唯一权威来源；其他活动文件通过引用、生成或解析式测试与它保持一致。
3. 机器需要消费的配置使用 JSON、Schema、TOML 或确定性脚本承载；说明文档解释含义和边界，不手写第二份可漂移映射。
4. 项目特例留在项目级文件，不在公共 Skill 中增加永久例外。
5. 若根因修复会影响多个消费者，应一次更新所有受影响的活动文件、Schema、模板、示例、测试和用户说明。

## 3. 变更前分类

修改前把相关文件标记为：

- **canonical**：唯一权威来源；
- **generated**：由 canonical 生成，可重新构建；
- **consumer**：读取或引用 canonical；
- **historical**：变更历史、复盘、失败记录或已发布说明；
- **temporary**：可验证、可恢复且不再被引用的临时产物。

不得直接修补 generated 文件而不修生成链。不得把 historical 文件当活动实现删除或改写为“从未发生”。

## 4. 最小完整变更

1. 检查 Git 状态并保护用户已有改动；无法安全隔离时停止。
2. 修改前新增或更新能暴露缺陷的回归测试，并确认旧实现确实失败。
3. 实施满足验收条件的最小完整修复，不顺带重构无关区域。
4. 对重复规则，保留 canonical 定义，把消费者改为引用或生成；不要仅增加“保持同步”的文字提醒。
5. 对兼容层写明所有者、适用边界、验证方式和退出条件。没有真实兼容需求时不新增兼容分支。
6. 修改后先运行最小相关测试，再运行全量静态检查、编码检查和必要的行为评测。
7. 变更方案和交付摘要必须显式说明历史追溯入口：至少指出 Git、CHANGELOG、项目复盘或等价载体中的实际承载位置；不得只写“保留历史”而不给定位。
8. 仓库级实质性优化还应在 `update-history/` 新增一条独立记录并更新索引；`CHANGELOG.md` 只保留版本级摘要，二者不得互相替代。

## 5. 清理边界

只有同时满足以下条件，才可清理临时或过时活动文件：

- 已精确枚举目标，确认不包含链接、原始数据、科研无损区或用户未提交工作；
- 全仓引用检查为空，替代路径已验证；
- 相关回归测试通过；
- 文件确属 generated、temporary 或已明确弃用的兼容产物；
- material artifact 的删除已获得用户授权，并优先采用可恢复方式。

被 Git 历史、CHANGELOG、项目复盘或证据定位承载的历史无需复制到活动目录；但这些追溯入口必须保留。

## 6. 交付验收

变更交付前至少核对：

- 行为、Skill、Schema、配置、模板、示例、测试和说明是否一致；
- canonical 与 generated 产物是否通过哈希或解析式检查；
- 是否仍有失效引用、重复映射、无退出条件的兼容层或未解释的中间文件；
- 科研无损区、用户改动和版本历史是否保持完整；
- 回滚定位、未解决项和下一动作是否明确。

若任何关键消费者仍依赖旧契约，返回 `REVISE`；若会覆盖用户工作、破坏科研追溯或无法安全确定删除目标，返回 `BLOCKED`。

质量门答复必须显式输出一个标准结论词：`PASS`、`CONDITIONAL PASS`、`REVISE` 或 `BLOCKED`。不能用“暂不继续”“建议修复”等近义表述代替机器可判定状态。
